# Нотлох баримтыг шинжлэх

[English](ANALYSIS.md) · [← README](../README.mn.md)

## Sigma hunter-т дамжуулах

Үйл явдлын логийн модуль нь өндөр дохиотой 15 event ID тутамд
`EventLogs\evt_<ID>.csv` бичиж, тус бүрийг 50 event-ээр хязгаарлана. Энэ нь
triage хийж байх үедээ шууд уншихад зориулсан урьдчилсан харагдац. Зориудаар
жижиг бөгөөд **hunting-ийн өгөгдлийн сан биш** — энэ бол түгээмэл буруу
ойлголт учир ил хэлэх нь зүйтэй.

Sigma дүрмийг бүх түүхэн лог дээр ажиллуулахыг хүсвэл `-ExportEvtx` нэм. Тэгвэл
`Security.evtx`, `System.evtx`, `Application.evtx`, Sysmon суулгасан бол
`Sysmon.evtx`-г мөн тэр `EventLogs\` хавтас руу бичнэ. CSV биш, яг EVTX бол
[Hayabusa](https://github.com/Yamato-Security/hayabusa) болон
[Chainsaw](https://github.com/WithSecureLabs/chainsaw)-ийн оролтоор авдаг
формат. Тиймээс тэр хавтсыг аль алинд нь хэвээр нь дамжуулж болно:

```bash
hayabusa csv-timeline -d EventLogs/ -o timeline.csv
chainsaw hunt EventLogs/ -s sigma/ --mapping mappings/sigma-event-logs-all.yml
```

`-ExportEvtx` анхдагчаар унтраалттай, учир нь бүрэн лог экспортлох нь чимээ
шуугиантай бөгөөд хааяа тэмдэглэгддэг — [AV / EDR аюулгүй
байдал](AV-SAFETY.md)-ыг үз.

Ажлын хуваарилалт нь гол санаа. TATAR нь *энэ хост яг одоо ямар төлөвтэй байна
вэ* гэдэгт хариулдаг; Sigma хөдөлгүүр нь *бүх логийн түүхэнд юу таарсан бэ*
гэдэгт хариулдаг. Эдгээр нь өөр асуултууд бөгөөд энэ хавтас нь хоёр төрлийн
шинжилгээний үр дүнг холбох үүрэгтэй.

## Нотлох баримтын хамаарал

Нэг artifact дангаараа зөвхөн сэжүүр болно. Харин хоёр бие даасан artifact ижил
**file path** зааж байвал энэ нь илүү хүчтэй нотолгоо болно. Хэрэгсэл 1.5.0 хүртэл
энэ мэдээллийг ашиглалгүй хаядаг байв: MOTW «татагдсан» гэж хэлж буй файл,
UserAssist «ажиллуулсан» гэж хэлж буй файл хоёр нэг файл мөн гэдгийг шинжээч
нүдээрээ анзаарах ёстой байсан.

Correlation дүрмүүдийг зориудаар **цөөн байлгаж, тус бүрд нь тодорхой нэр өгсөн**. «Давхцсан бүхнийг» үзэх ерөнхий
дүрэм бол тохиолдлыг нотолгоо гэж нэрлэх явдал — энэ төслийн байнга залруулдаг
алдаа (эхний `useractivity` хувилбар 144 finding гаргасны 142 нь дуу чимээ
байсан). Дүрэм зөвхөн **өөр өөр модулийн** хоёр finding нэг зам нэрлэсэн үед л
ажиллаж, тэр зөвшилцөл юу гэсэн утгатайг үгээр хэлнэ.

| Дүрэм | Хэзээ ажиллах | Ямар утгатай |
|-------|---------------|--------------|
| **COR-01** `download-then-execute` | `motw` ба `useractivity` нэг зам нэрлэвэл | интернэтээс ирсэн файл бас ажиллуулагдсан |
| **COR-02** `autorun-on-suspect-file` | `persistence` ба (`motw` эсвэл `indicators`) нэг зам нэрлэвэл | autorun бичлэг нь өөрөө сэжигтэй файл заасан |

`prefetch` ба `autoruns` эхэндээ эдгээр дүрэмд нэрлэгдсэн байсныг хассан: хоёул
тайланд цуглуулдаг ч аль нь ч finding гаргадаггүй тул тэр хагас нь энэ хүснэгт
ажилладаг гэж бичиж байхад хэзээ ч ажиллах боломжгүй байв. Gate одоо finding
гаргадаггүй модуль нэрлэсэн дүрмийг зөвшөөрөхгүй.

COR-01 нь зөвхөн Windows: Mark-of-the-Web бол NTFS-ийн alternate data stream
бөгөөд Linux дээр файл интернэтээс татагдсаныг тэмдэглэдэг ижил механизм байхгүй. Энэ ялгааг
`check_docs_parity.py` дотор зарласан ба тэр нь мөн дүрэм байхгүй болсон модуль
нэрлэвэл build-ийг унагаана — тэтгэвэрт гарсан модуль заасан дүрэм чимээгүй
ажиллахаа болих ба шинжээч өсөөгүй итгэлийг *хоёр артефакт хоорондоо нийцээгүй*
гэж буруу ойлгоно.

**Юуг өөрчилдөг, юуг өөрчилдөггүй.** `confidence`-ийг **0.85** болгож,
`confidenceReason`-д дүрэм, хоёр модуль, нийтлэг зам, нөгөө finding-ийн id-г
бичнэ. Severity-д **хүрэхгүй**, finding-үүдийг нэгтгэхгүй, шинээр үүсгэхгүй:
хамаарал нь байгаа сэжүүрийг илүү итгэлтэй болгоно, шинэ мэдэгдэл хийхгүй.
Шатлал нь `0.4` Review → `0.7` High → `0.85` хамаарсан → `0.95` IOC-оор
батлагдсан.

Энэ нь **хамгийн сүүлд**, allowlist болон IOC-ийн дараа ажиллаж, дарагдсан
finding-ийг — allowlist тэр замыг аль хэдийн «мэдэгдэж байгаа цэвэр» гэж
шийдсэн тул түүн дээр хамаарал үзэх нь яг л устгасан дуу чимээг буцааж өсгөнө —
мөн IOC таарсныг (түүний `0.95` нь `0.85`-аас дээгүүр) алгасна.

Хоёр хувилбар жижиг/том үсгийн асуудал дээр **зориудаар зөрдөг**:
`C:\Temp\X.EXE` ба `c:\temp\x.exe` бол нэг файл тул заавал хамаарах ёстой;
`/tmp/x` ба `/Tmp/X` бол өөр файл тул хамаарч болохгүй. Хоёулангийнх нь тохиолдол
хоёр платформ дээр шалгагдсан.

## Цуглуулалт дууслаа. Одоо яах вэ?

Эхний шатны хариу арга хэмжээ авагчийн хамгийн хэцүү асуулт нь *юу ажиллуулах вэ* биш,
*хавтас гарлаа, одоо яах вэ* гэдэг. Гурван гаралт үүнд хариулна, мөн
эдгээрийг гаргахад цуглуулалтын явцад нэмэлт ачаалал үүсэхгүй.

| Файл | Юунд зориулагдсан |
|---|---|
| `ARTIFACTS.md` | Энэ ажиллагааны гаргасан файл бүр, тэр нь ямар асуултад хариулдаг, юугаар нээх вэ — `.evtx` → Hayabusa/Chainsaw, `.lnk` → LECmd, jump list → JLECmd, hive → RegRipper. Бодитоор гарсан файлуудаас барьдаг тул бага цуглуулсан ажиллагаа бага зүйл хэлнэ. |
| `paste.txt` | Бүтэн ажиллагаа 60-аас цөөн мөрөөр — тикет, чатад наагаад *«энэ хэвийн үү?»* гэж асуухад зориулсан. |
| `allowlist.suggested.json` | Энэ хостын finding-үүдээс гаргасан allowlist-ийн **ноорог**, `-Allowlist` уншдаг форматаар. |

**`paste.txt` зориудаар тогтвортой.** Үргэлжлэх хугацаа, тоолуур, процессын id
орохгүй; finding-үүд илрүүлсэн дарааллаар биш, severity → ангилал → мессежээр
эрэмбэлэгдэнэ. Ажиллагаа бүрт хоёр мөр өөрчлөгдөх ба түүнийгээ өөрөө хэлнэ.
Тиймээс хоёр paste лог-ийн diff нь **хост** дээр юу өөрчлөгдсөнийг харуулна,
цаг юу хийснийг биш — HijackThis-ийн лог-ийг арван жил ашигтай байлгасан яг тэр
шинж. Дараалан хоёр удаа ажиллуулж шалгасан: яг зарласан хоёр мөр л зөрсөн.

**Allowlist-ийн ноорог бол ноорог.** Энэ хостын finding-үүдэд дурдсан бүх
замыг жагсаана, юуг ч шүүхгүй. Итгэдэг build-ээсээ аваад, батлан хэлж чадахгүй
мөрүүдээ устгаад, дараа нь бүх хост дээр уг allowlist-ийг ашиглан
ажиллуулбал зөвхөн ялгаа л харагдана. Хэн ч шалгаагүй хостоос авсан baseline нь яг таны хайж байсан
халдлагыг дарна — файл өөрөө эхний талбартаа үүнийг бичсэн шалтгаан нь тэр.

**Артефактын толь бичиг gate-тэй.** Энэ бол гараар арчилдаг нэрсийн жагсаалт
бөгөөд энэ репо аль хэдийн таван хуучирсан жагсаалт гаргасан. Тиймээс
`ARTIFACTS.md` нь машинд шалгагдах `Uncatalogued: N` мөрөөр төгсөж, CI нь `0`-
ээс өөр утгатай бол build амжилтгүй болно: хэн ч тайлбарлаагүй файл бичиж эхэлсэн модуль build-ийг
унагаана, тайлбаргүй артефакт чимээгүй гаргахын оронд.

## Finding-ийг харах (`tools/viewer.html`)

`summary.json` эсвэл `findings.json`-ийг **өөрийн шинжилгээний машин** дээр уншихад зориулсан ганц статик хуудас: browser-т нээгээд файлаа чирж оруулна. Сүлжээнд хандахгүй (Content-Security-Policy нь `default-src 'none'`), утга бүрийг текстээр л зурна, collector-т юу ч нэмэхгүй тул collector, түүний хурд, AV surface өөрчлөгдөхгүй.

Finding бүрт confidence-ийг нэрээр нь (Review, High, Correlated, IOC) шалтгаантай нь, батлагдсан technique ID-аас үүссэн ATT&CK холбоос, finding-ийн нэрлэсэн path-ууд, мөн `artifactClass`-ийн дараагийн алхмыг үзүүлнэ: юу асуух, хаана харах, юу нь ихэвчлэн хэвийн, хэзээ escalate хийх. Guidance 46 ангилал бүрийг хамарсан, холбоос агуулаагүй, хохирсон host дээр юм ажиллуул гэж хэзээ ч хэлэхгүй. Finding-ийн дээр collector-ийн **хийж чадаагүй** зүйлийг — алгассан module, дуусаагүй module (`moduleStatus`), хязгаарлалт — гаргана, учир нь тэдгээргүйгээр хоосон жагсаалт юу ч хэлэхгүй.

`.github/scripts/check_viewer.py` нь CI gate: policy-ийн hash файлтай таарах, script нь HTML-string sink, сүлжээний дуудлага, storage ашиглахгүй байх, файл цэвэр ASCII байх, guidance нь хаалттай `artifactClass` олонлогтой яг таарах ёстой. `tests/test-viewer.py` (Playwright хэрэгтэй) нь хортой `findings.json` файлуудыг ачаална. Viewer-ийн script эсвэл style-ийг зориуд өөрчилсний дараа `python .github/scripts/check_viewer.py --seal` нь policy hash-ийг шинэчилнэ.
