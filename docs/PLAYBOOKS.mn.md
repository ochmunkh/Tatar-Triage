# Шинжээчийн playbook: finding-тэй юу хийх вэ

[English](PLAYBOOKS.md) · [← README](../README.mn.md)

Finding бүр `recommendation` агуулдаг: ангилалаар нь сонгогдсон нэг өгүүлбэр ([TOOLS.md](TOOLS.md)). Энэ хуудас ижил ангиллуудыг авч өгүүлбэр бүрийг богино дэс дараалал болгон өргөтгөнө. Энэ бол зохиогчийн ажлын туршлага, стандарт биш бөгөөд finding нь үргэлж хянах зүйл (lead), шийдвэр биш.

## Playbook-ийг хэрхэн хэрэглэх вэ

1. `summary.txt` дэх finding-ийг унш: мессеж, дэлгэрэнгүй, нэрлэсэн тайлангийн хэсэг. `TATAR_Report_<HOST>_<stamp>.txt`-ийг тэр хэсэгт нээж нотлох баримтыг өөрөө хар.
2. Доорх ангилалд тохирох playbook-ийг дага. Нотлох хавтасны хуулбар дээр ажилла.
3. Шийдэхээсээ өмнө асуултаа тэлэ: энэ fingerprint бусад хост дээр байсан уу (`tools/tatar-aggregate.py`), өмнөх сканд байсан уу (`tools/tatar-diff.py`), яг тэр үед өөр юу болсон бэ (`tools/tatar-timeline.py`)?
4. Хариултаа `tools/tatar-review.py`-аар (`good`, `suspicious`, `bad`) бүртгэ, дараагийн сканд дамжина.
5. Хостыг цэвэр гэхээсээ өмнө `tatar.log`-ийг унш: юу цуглуулаагүйг жагсаасан байдаг.

Нэг finding олон хост дээр байвал, файл эсвэл бичилт шалгаж буй цагийн хүрээнд гарч ирсэн бол, эсвэл эзэмшигч тайлбарлаж чадахгүй бол дээш шилжүүл. Лийдийг `good` гэж зөвхөн яагаад байгааг мэдэж байвал хаа.

## Windows ба Linux

### process
1. Finding-д харагдах image path, гарын үсэг, parent process, сүлжээний холболтыг тэмдэглэ.
2. Binary-г хэшле (Windows дээр `binary_hashes.txt` ажиллаж буй binary-ийн хэшийг жагсаадаг) бөгөөд process-ийг дуусгахаасаа өмнө хэшийг өөрийн эх сурвалжаар хайж үз.
3. Ижил fingerprint бусад хост дээр байгаа эсэхийг шалга. Хэрэглэгч бичиж болох хавтас дахь гарын үсэггүй binary, үл мэдэгдэх parent, гадагш холболттой бол дээш шилжүүлэх шалтгаан.

### persistence
1. Бичилтийг хэн, хэзээ үүсгэснийг тайлангийн хэсгээс болон тухайн үеийн `timeline.csv`-ээс ол.
2. Түүний ажиллуулдаг зүйлийг хэшлээд мэдэгдэж буй цэвэр build-тэй харьцуул.
3. Юуг ч устгахаасаа өмнө бичилтийг тэмдэглэ; устгавал хэзээ ажилласан тухай нотлох баримт устна.

### privesc
1. Энгийн хэрэглэгч finding-д нэрлэсэн зам эсвэл тохиргоонд бичиж чадахыг батал.
2. Эрхийг засах эсвэл замыг хашилтад ав, дараа нь дахин скан хийж finding алга болсныг батал.
3. Зам нь өндөр эрхээр ажиллах үйлчилгээнд харьяалагддаг бөгөөд файл саяхан бичигдсэн бол дээш шилжүүл.

### lateral
1. Тохирох logon үйл явдлаас эх хост болон акаунтыг тодорхойл.
2. Бусад хост дээр ижил хэрэгсэл эсвэл олдворыг `tools/tatar-aggregate.py`-аар хайж үз.
3. Хоёр ба түүнээс олон хост дээр харагдвал дээш шилжүүл.

### rmm
1. Энэ remote-management хэрэгслийг зөвшөөрсөн эсэхийг эзэмшигчээс асуу.
2. Зөвшөөрөөгүй бол устгахаасаа өмнө finding доторх холболтын түүхээр хэзээ, ямар акаунтаар суулгасныг тэмдэглэ.
3. Холболтын мөртэй, зөвшөөрөлгүй remote-access хэрэгсэл бол дээш шилжүүлэх шалтгаан.

### useractivity
1. Хэрэглэгчээс өөрөө ажиллуулсан эсэхийг асуу.
2. Файл хаанаас ирсэн, хэзээ анх гарч ирснийг шалга (доорх `motw`-ийг хар).
3. Run цонхонд бичсэн, цонхыг нууж буй команд бол хаахаасаа өмнө хоёр дахь нүдээр харуулах хэрэгтэй.

### obfscan
1. Скриптийг аюулгүй газар хуулж, ажиллуулалгүйгээр задал.
2. Татах команд, кодлогдсон payload, тэдгээрийн заасан хаягийг ол.
3. Юуг ч устгахаасаа өмнө файлын хэш болон хаанаас ирснийг тэмдэглэ.

### indicators
1. Файлыг хэшлээд хаанаас ирсэн, хэзээ үүссэнийг шалга.
2. Хортой гэж үзэхээсээ өмнө allowlist-тэй харьцуул; суулгагч, шинэчлэгч ч temp хавтсанд бичдэг.
3. `.pdf.exe` шиг давхар өргөтгөл нь сонгодог өнгөлөн далдлалт; тайлбарлагдтал онцгой анхаарал тавь.

### motw
1. Татаж авсан эх сурвалжийг шалга.
2. Дараа нь нээсэн эсвэл ажиллуулсан эсэхийг шалга (Windows дээр `useractivity` ба `prefetch`).
3. Татаж аваад ажиллуулсан executable нь зөвхөн хадгалсан баримтаас илүү анхаарал татна.

### network
1. Бичилтийг энэ хост хэрэглэх ёстой зүйлтэй харьцуул; hosts файлын override эсвэл өөрчилсөн resolver урсгалыг өөр тийш чиглүүлж чадна.
2. `hosts.txt`, `dns_cache.txt`, `ipconfig.txt`-ийг хамт унш.
3. Эзэмшигчийн нэмээгүй нэвтрэх, шинэчлэх эсвэл банкны хаяг бичилтэд байвал дээш шилжүүл.

### sessions
1. Logon үйл явдлын эх хаяг болон зорилтот акаунтуудыг жагсаа.
2. Дараа нь аль нэг оролдлого амжилттай болсон эсэхийг шалга.
3. Нэг хаягаас олон бүтэлгүйтлийн дараа амжилт гарсан бол дээш шилжүүл.

### users
1. Акаунт хүлээгдэж байсан эсэх, хэн хэзээ үүсгэснийг батал.
2. Хэрэггүй бол нууц үг тавь эсвэл акаунтыг идэвхгүй болго.
3. Чиний үүсгээгүй шинэ administrator бол дээш шилжүүлэх шалтгаан.

### eventlogs
1. Лог зориуд цэвэрлэгдсэн эсвэл зогссон эсэхийг шалга.
2. Collector руу дамжуулсан хуулбар байгаа бол түүнтэй харьцуул.
3. Цэвэрлэгдсэн security лог өөрөө өндөр анхаарал татна; цэвэрлэсэн цагийн өмнөхөн юу болсныг хар.

### ioc
1. Өөрийн indicator жагсаалтаас гарсан таарал: санамсаргүй давхцал биш эсэхийг батал.
2. Бусад хостоос ижил indicator-ыг хай.
3. Харьцуулсан feed-ийн хувилбарыг хадгал, ингэвэл үр дүнг давтаж чадна.

### бусад ангилал
Finding-д нэрлэсэн нотлох баримтын хэсгийг унш, хүлээгдэж байсан эсэхийг эзэмшигчээс батал.

## Зөвхөн Linux

### suid
1. Файлыг багц менежертэй тулга.
2. Setuid бит агуулах ёстой эсэхийг батал.
3. Хэрэглэгч бичиж болох замд, ямар ч багцад харьяалагдаагүй setuid файл бол дээш шилжүүлэх шалтгаан.

### sshkeys
1. Түлхүүр бүр мэдэгдэж буй хүн эсвэл системд харьяалагддагийг батал.
2. `authorized_keys` хамгийн сүүлд хэзээ өөрчлөгдсөнийг шалга.
3. Хэн ч нэрлэж чадахгүй түлхүүр бол дээш шилжүүлэх шалтгаан.

### bashhistory
1. Татах, нууц үг ашиглах, цэвэрлэх командуудыг тойрсон команд ба цагийн тэмдгийг унш.
2. Түүх бол хэрэглэгчийн өөрийн бүртгэл бөгөөд засаж эсвэл унтрааж болохыг санаарай.

### context
1. Энэ хост контейнер ажиллуулах ёстой эсэх, эсвэл контейнер дотор байгаа эсэхийг батал.
2. Холбосон замууд болон эрхийг хянах.
3. Энэ хостын бусад finding-ийг биет машины бус контейнерийн тухай finding гэж унш.
