## Архитектур

TATAR бол ижил үүрэгтэй хоёр хувилбар — `Tatar.ps1` (Windows, 33 модуль), `tatar-linux.sh` (Linux, 18 модуль) — боловч хоёул ижил гаралтын contract-тай. Ижил JSON schema (`schemaVersion 1.7`) гаргадаг тул SIEM/SOAR аль ч платформын үр дүнг ялгалгүй уншина.

```
                    TATAR Triage
                         │
          ┌──────────────┴──────────────┐
     Windows · Tatar.ps1           Linux · tatar-linux.sh
     (PowerShell, 33 модуль)       (Bash, 18 модуль)
          └──────────────┬──────────────┘
                         ▼
     Хувийн нотлох хавтас · terminal-д аюулгүй тайлан
                         ▼
             Нэгдсэн JSON schema  (summary.schema.json · v1.7)
                         ▼
   ┌───────────────┬─────┴─────────┬───────────────────┐
   ▼               ▼               ▼                   ▼
 summary        findings        timeline        manifest + digest
(+ тайлан)   (+ moduleStatus)  (+ hashes)       (sha256sum -c)
   └───────────────┴─────┬─────────┴───────────────────┘
                         ▼
      tools/viewer.html (офлайн)  ·  SIEM / SOAR
                         ▼
              DFIR мөрдөн шинжилгээ
```

### Өгөгдлийн урсгал

1. Аргумент уншиж, хувийн гаралтын хавтас (symlink/junction зам, эсвэл аль хэдийн байгаа нотлох хавтсыг татгалзана) болон chain of custody-г бэлдэнэ.
2. Ажиллаж буй орчноо (виртуал / контейнер / хамгаалалт) тодорхойлно.
3. Модулиудаа **volatility-ийн дарааллаар** (RFC 3227) ажиллуулна (санах ой · сүлжээ · процесс → диск · registry · лог). Модуль бүр түүхий нотолгоог диск рүү, бүтэцтэй finding-ийг санах ойд гаргана.
4. **Allowlist** нь урьдаас мэдэгдэж байгаа цэвэр зүйлсийг нууна — устгахгүй, аудитад үлдээнэ.
5. **IOC** нь мэдэгдэж байгаа хортой индикаторыг тэмдэглэж, allowlist-ийг давж, цуглуулсан нотолгоонд тулгуурлан шинэ finding үүсгэнэ.
6. Идэвхтэй / suppressed гэж эрэмбэлж `summary.txt` / `summary.json` (модуль бүрийн `moduleStatus[]`-тай), `findings.json`-ийг бичиж, үүсгэсэн текст дэх control/bidi тэмдэгтийг саармагжуулан, SHA-256 manifest болон түүний өөрийн digest-ийг бичнэ. `tools/viewer.html` JSON-г офлайнаар уншина.

### Finding загвар

Finding бүр нэг бичлэг бөгөөд платформ хооронд ижил бүтэцтэй: `id` · `severity` (High/Review) · `category` · `technique[]` (MITRE) · `message` · `detail` · `confidence` (0.7 High · 0.4 Review · 0.95 IOC-баталгаажсан) · `suppressed` · `suppressReason` · `iocMatch` (boolean; таарсан индикатор нь `detail`-д `IOC match: <indicator> | ...` хэлбэрээр бичигдэнэ). Suppressed finding нь тайлан болон JSON-д шалтгаантайгаа үлдэнэ — зөвхөн идэвхтэй жагсаалтаас хасагдана, бичлэгээс арилдаггүй.

### Allowlist — дуу чимээнээс дохиог ялгах

Мэдэгдэж байгаа цэвэр зүйлсийг зам, Authenticode нийтлэгч (Windows), `dpkg`/`rpm` багц эзэмшил (Linux), эсвэл SHA-256-аар нууна. Цэвэр хост дээр хийсэн нэг run-д 11 finding-ээс **4 нь идэвхтэй, 7 нь suppressed** болсон.

### IOC — known-bad нь allowlist-ийг давна

Offline `hashes / ips / domains / filenames` жагсаалт авна (`hashes` нь зөвхөн SHA-256 — MD5/SHA-1 харьцуулагдахгүй). *Pass A* нь одоо байгаа finding-уудтай тааруулж, таарвал **allowlist-ийг давж** тухайн finding-ийг дахин идэвхжүүлэн High / 0.95 болгоно. *Pass B* нь цуглуулсан нотолгооноос олдсон IOC-д зориулж шинэ finding үүсгэнэ, technique-ийг indicator-ийн төрлөөр тавина — IP → `T1071`, domain → `T1071.004`, filename → `T1204.002`, hash → `T1588.001`. Зарчим энгийн: мэдэгдэж байгаа хортой индикатор үргэлж цэвэр allowlist-ийг давна.

Feed-ийн хоёр замыг **цуглуулга эхлэхээс өмнө** шалгана. Уншигдахгүй замыг чимээгүй өнгөрөөхгүй: консол дээр сануулж, error бүртгэж, exit code `2` болгоно — тиймээс файлын нэрэн дээрх нэг үсгийн алдаа шинжээчийг "идэвхтэй finding байхгүй" гэж эндүүрэхэд хүргэж, гэтэл feed огт ажиллаагүй байх нөхцөлд хэзээ ч оруулахгүй.

### Trust boundary

Сүлжээгээр юу ч илгээхгүй — allowlist, IOC жагсаалт нь дотоод файл, хэш дотооддоо бодогдоно. Зөвхөн уншина; root/Admin нь уншиж болох хүрээг өргөтгөнө, өөрчлөх эрх нэмдэггүй. Скриптийн өөрийн SHA-256 болон хувилбарыг (`summary.json`-ийн `version`) chain of custody-д бичих ба EDR-т мэдрэг үйлдлүүд (memory dump, hive save, устсан файлын өгөгдлийг сэргээн гаргах) анхдагчаар унтраалттай, тухайлан асаадаг. Нотлох хавтас нь шинжээчид хувийн, хостоос авсан текст (файлын нэр, command line) тайланд орохын өмнө саармагжуулагдаж, түр файл устгагдана; эдгээрийг тус бүрд нь [docs/SECURITY-TESTING.md](SECURITY-TESTING.md)-д тэмдэглэсэн тест баталгаажуулна.

## Нууцлал

Tatar Triage бүрэн **офлайн** ажиллана. Цуглуулсан мэдээлэл, scan үр дүн, хэрэглэгчийн өгөгдлийг ямар нэг сервер рүү **илгээдэггүй**.
